PART 2 - LOGIN IS NOT WORKING: DIAGNOSE, THEN FIX
==============================================================================
Static reading shows the request/response contract is consistent (Flutter sends
{email,password} to /api/auth/login and expects {token, refresh_token,
expires_at}; the API returns exactly that). So the failure is environmental or
in error handling, not a field-name mismatch. Work through these IN ORDER and
record the result of each step in docs/login-diagnosis.md.

2.1  Which build is the user running?  (most likely cause)
     - N-4: the CI/Release APK targets http://10.0.2.2:3000. On a phone this
       fails with a connection error and the AuthScreen shows the raw exception
       text. Verify: add a visible "Server: <API_BASE_URL>" line to the app's
       About/debug screen, or run `strings` on the APK for 10.0.2.2.
     - FIX: make API_BASE_URL mandatory in release/profile builds and in every
       CI build (fail the build if absent; one build workflow, not two). Debug
       defaults may stay 10.0.2.2 ONLY when running on an emulator.

2.2  Is the server actually up and configured?  Run, and paste outputs:
       curl -i https://unadomot.fly.dev/health
       curl -i https://unadomot.fly.dev/ready
       curl -i -X POST https://unadomot.fly.dev/api/auth/register \
            -H 'content-type: application/json' \
            -d '{"email":"probe+1@example.com","password":"Probe-pass-1234","name":"Probe"}'
       curl -i -X POST https://unadomot.fly.dev/api/auth/login \
            -H 'content-type: application/json' \
            -d '{"email":"probe+1@example.com","password":"Probe-pass-1234"}'
       fly logs -a unadomot   |   fly secrets list -a unadomot   |   fly status
     Interpretation:
       - /ready not 200 or 503 JSON  => DATABASE_URL missing/wrong (the API is in
         "Unconfigured" mode) or Neon unreachable. Required secrets:
         DATABASE_URL (Neon DIRECT host, sslmode=require, NOT -pooler),
         JWT_SECRET, REFRESH_TOKEN_SECRET.
       - connection timeout on first call => cold start (N-5).
       - 429 => rate limiter (shared "unknown" bucket behind the proxy).
       - 401 invalid_credentials for a user just registered => hashing/lookup
         bug: check lower(email) handling and the password-hash column.
     FIXES (do all, they are independent):
       a. Fail fast: if DATABASE_URL is missing (or any production-required
          secret), the process must exit(1) with a clear message. Delete the
          Unconfigured* adapters from the production path (T-CONFIG in v1).
       b. fly.toml: min_machines_running = 1 for the beta (no cold starts).
          Move migrations out of boot into a release_command
          (`[deploy] release_command = "unadomot-api migrate"`).
       c. Client: increase connect timeout to 30 s for the FIRST auth call, show
          a "Waking the server..." state after 6 s, auto-retry once.
       d. One fly.toml + one Dockerfile (services/api/*); delete the root copies
          or make the root ones the only ones and fix the workflow context.

2.3  Client-side login logic bugs (fix regardless of 2.1/2.2):
     - ApiClient.authenticate() throws FormatException('Invalid session
       response') if the server's expires_at is not after the DEVICE clock. A
       phone whose clock is slow (or a wrong timezone/date) can never log in.
       Never compare server timestamps to the local clock to validate a session:
       trust the server response; compute remaining life from `expires_in` or
       from (expires_at - server Date header).
     - `signedIn` is derived from local expiry, so the whole UI flips between
       screens on a timer-less getter. Replace with an explicit AuthStatus
       (signedOut | signedIn | refreshing) held in AppState and driven by
       events (login, refresh failure, logout, 401 after refresh).
     - AuthScreen displays error.toString(). Map failures to friendly copy:
       no network -> "Can't reach UnaDomot. Check your connection."; timeout ->
       "The server is waking up. Try again."; 401 -> "Invalid email or
       password."; 429 -> "Too many attempts. Try again in a minute."; 5xx ->
       "Something went wrong on our side." Never show stack/exception text.
     - Flutter secure storage on some devices throws on first read/write; wrap
       in try/catch and degrade to in-memory session instead of failing login.

2.4  Backend login hardening required to call login "working":
     - login() must return the user (drop the second find_by_email in
       login_handler).
     - Constant-time behaviour for unknown users (dummy Argon2 verify) and
       spawn_blocking for Argon2.
     - Do not log emails; log a hashed/truncated identifier.
     - Map unique-violation on register to 409, repository errors to a logged
       5xx with request id (T-LOG).

2.5  Acceptance for login (all must be demonstrated):
     - Backend router tests (tower::ServiceExt::oneshot, real Postgres): register,
       login ok, wrong password 401, unknown email 401 with same body/timing
       class, suspended user 401/403, rate-limited 429.
     - Flutter tests with a fake client: success, wrong password message, no
       network message, timeout message, clock-skew device still logs in.
     - Emulator/device smoke test against a locally running compose stack AND
       against the Fly URL, recorded in docs/evidence/login.txt with the exact
       commands and outputs.
     - A release-mode APK installed on a real phone logs in against the live API
       (human action H-LOGIN in Part 7).

PART 3 - THE USER JOURNEY: WHERE THE REWRITE GOT IT WRONG
==============================================================================
Legacy = `main` branch (React/Firebase PWA). Rewrite = this branch.
Auth-gate rule in the legacy code: `useRequireAuth` / `window.__openAuthModal`
opens a modal (login | signup | post) over the current page, remembers
`redirectPath` and intent props (listingId, openPostAfterLogin, email) and
resumes the action afterwards. Nothing blocks the home page.

STEP 0 - Launch
  Legacy : splash screen on #f0fdf4 with the UnaDomot logo, then fades the app
           in (#root opacity transition 0.3s). App is installable (manifest,
           "Install" button), works offline (service worker + offline.html).
  Rewrite: no splash, no branding; plain Material app. WRONG: no brand moment,
           no offline page.

STEP 1 - First screen
  Legacy : HOME - open to everyone. Header (desktop: search bar with filter icon
           and suggestions, action buttons; mobile: bottom navigation bar),
           featured carousel, "Recently viewed", listing grid, grid/map toggle,
           "other locations" section, footer (desktop/web).
  Rewrite: `state.signedIn ? ListingsScreen : AuthScreen`. A new user sees
           "Sign in" and nothing else. WRONG (blocking): this is the single
           biggest UX failure. Also WRONG: after the access token expires the
           same getter flips the app back to the login wall.

STEP 2 - Discover (search / filter / map)
  Legacy : search with location suggestions; Filter Listings panel with State,
           (LGA), Bedrooms, Type (Apartment/House/Self Contain/Room/Duplex),
           Furnishing (Furnished/Semi-furnished/Unfurnished), Sort (Smart ...),
           price range slider, toggles "Agent Only" and "No Fees", buttons
           "Clear" and "Apply Filters"; Grid <-> Map view toggle remembered
           (localStorage home_view_mode); map with clustering and popups;
           infinite loading with skeleton cards.
  Rewrite: a single list, first page only, no search, no filters, no map, no
           infinite scroll. WRONG/MISSING.

STEP 3 - Open a listing
  Legacy : image gallery + lightbox, price/title/address, badges, property
           details, amenities, description, landlord card (verification badge,
           role badge), message button, report button, share, comments and
           reactions, similar listings.
  Rewrite: basic detail; "Chat with lister" does nothing; no report, share,
           gallery lightbox, similar listings. WRONG/MISSING.

STEP 4 - Anonymous user taps a protected action
  Legacy : (favorite heart, message, post, comment, react, verification, report,
           and the Favorites/Messages/Profile/Post nav items) -> auth modal
           opens in place; after login the intended action continues.
  Rewrite: there is no anonymous state to tap from. WRONG (see Step 1).

STEP 5 - Sign in / Sign up
  Legacy : modal (max-w-md, rounded-2xl, dark backdrop with blur). TWO-STEP
           login: step 1 email ("Email Address", placeholder you@example.com) +
           "Continue with Google"; button "Continue ->" (shows "Checking...");
           if the email has no account it flips to Sign up; step 2 password
           (placeholder bullets) with "Forgot password?". Footer: "New to
           UnaDomot? Create account" / "Already have an account? Sign in".
           Signup has a password-strength meter and live validation; email
           verification page exists.
  Rewrite: one full page "Sign in / Create account" with default Material
           fields, raw error text, no Google, no forgot-password UI (backend
           endpoints exist), no strength meter, and login currently fails
           (Part 2). WRONG.

STEP 6 - Post a listing
  Legacy : modal wizard "Post a Listing" / "Edit Listing" (max-w-2xl, 95vh),

  Rewrite: a form screen nobody can reach; no wizard, no LGA mapping (state/LGA

STEP 7 - Favorites, Messages, Profile
  Legacy : Favorites page; Messages = chat list (unread badges) + chat view,

  Rewrite: favorites local only; basic inbox/chat (left-aligned bubbles, no

STEP 8 - Static and system pages
  Legacy : Privacy, Terms, Footer, 404 page, listing-by-code, share links,

STEP 9 - Loading, empty and error states

PART 4 - TARGET INFORMATION ARCHITECTURE AND AUTH-ON-DEMAND RULES
==============================================================================
4.1  Public (no account, no login wall, works offline from cache):
     Home (carousel, recent views, grid, map toggle, search, filters), Listing
     detail, Public profile, Privacy, Terms, Listing-by-code, shared links,
     404/"Listing Not Available".

4.2  Auth required (open the auth sheet IN PLACE, then resume the action):
     Favorite a listing . Message a lister . Post/Edit/Delete a listing .
     Report a listing/user . Comment/react . Request verification .
     Favorites tab . Messages tab . Profile tab . Notifications.
     Anonymous taps on those open the sheet; Post uses the SIGNUP variant with
     `openPostAfterLogin`; Favorites/Messages/Profile use LOGIN with a
     redirect to that tab. After success: close the sheet, perform the
     remembered intent (favorite it, open the chat, open the wizard).

4.3  Implementation (Flutter):
     - main.dart ALWAYS renders the Shell (Home). Delete the signedIn ternary.
     - `AuthGate.requireAuth(context, intent, {mode})` returns immediately if
       signed in, otherwise shows `AuthSheet` (modal bottom sheet on phones,
       dialog max 448 px on tablets) and returns a Future<bool>. `AuthIntent`
       carries: redirectTab, listingId, openPostAfterLogin, prefillEmail.
     - AuthSheet is two-step like the legacy modal (email + Google -> password /
       signup) with "Forgot password?", live validation, password strength
       meter on signup, friendly errors, and "Create account"/"Sign in" footer.
     - Session expiry never navigates away from the current screen: a failed
       refresh sets AuthStatus.signedOut and the next protected action prompts.
       Public screens keep working with cached data.
     - Deep links (https listing URLs) open Listing detail anonymously.

4.4  Acceptance: widget/integration tests prove (a) fresh install lands on Home
     with data and no login prompt; (b) tapping the heart anonymously opens the
     sheet and, after login, the listing is favorited; (c) Post as anonymous ->
     signup sheet -> wizard opens automatically; (d) token expiry mid-browse
     does not eject the user; (e) Messages tab anonymous -> login sheet ->
     lands on Messages.
