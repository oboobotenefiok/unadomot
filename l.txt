1. VERDICT
--------------------------------------------------------------------------------
Better, but still NOT production ready, and two of the "fixed" claims in
AUDIT-RESPONSE.md are false. The Flutter session layer is now genuinely solid and
the product surface has grown a lot (comments, reactions, calls, profiles, map,
codes). The growth is the problem: the ~2,000 lines of handlers added since pass 1
(profile, comments, rich messaging, calls) were written outside the layered
architecture, copy a weaker copy of the auth check, bypass rate limiting, leak
personal data, and have almost no tests.

Highest-impact findings, in order:
  1. Public profile endpoint leaks every user's EMAIL and PHONE (unauthenticated).
  2. The release APK is built without INTERNET/CAMERA/MIC/LOCATION permissions
     (and the scripts that add them don't exist). A release APK cannot reach the
     server. This is the most likely reason "login does not work" on the APK.
  3. Every push to the rewrite branch auto-deploys to production with no tests,
     and it deploys the OLD root Dockerfile (root user, no healthcheck).
  4. All new handlers skip rate limiting AND the suspended-account check.
  5. "My listings" and public-profile listings query price as f64 against a
     NUMERIC column (CONFIRM: likely 503 / silently empty).
  6. Cloudinary is not configured in production (your own checklist says so), so
     listing photos cannot be uploaded: the core flow is incomplete.

3. P0 - FIX BEFORE ANY USER TRAFFIC
--------------------------------------------------------------------------------

P0-A  Public profile leaks email and phone
  Where : services/api/src/profile_handlers.rs  ProfileRow::into_json() used by
          GET /api/profile/{username} (no auth).
  What  : The JSON includes "email" and "phone" for any user whose username is
          known. Anyone can scrape landlord contact details; this is a
          privacy/NDPA problem and defeats the in-app chat model.
  Fix   : Separate PublicProfile (id, name, username, photo, bio, user_type,
          verified, response stats, listings) from OwnProfile. Never serialise
          email/phone publicly. Add a test asserting the public JSON has no
          email/phone keys. Decide product-wise whether phone is shown only to
          signed-in users after an explicit "reveal".

P0-B  Release APK has no network permission (likely cause of broken login)
  Where : .github/workflows/build-apk.yml and build-apk-push.yml
  What  : They run `flutter create` and never add permissions. The generated MAIN
          manifest has no INTERNET (only the debug/profile manifests do), so a
          release APK cannot make a single request. The string INTERNET appears
          nowhere in the repo. The permission script the docs promise,
          scripts/apply_android_permissions.sh, DOES NOT EXIST; neither do
          apply_android_deep_links.sh, configure_android_signing.sh,
          migrate-firebase.mjs or migrate_legacy.py (all referenced by workflows
          or docs). Consequences: release.yml always fails at its first script
          step; rewrite-ci hides the missing script with continue-on-error; camera
          (listing photos, calls), microphone (voice notes, calls), location (map)
          and notifications would also fail on release builds.
  Fix   : Commit apps/flutter_app/android/ (stop regenerating it in CI) with the
          full permission set, deep-link intent filters and signing config; delete
          the hacks that patch plugin build.gradle files inside ~/.pub-cache.
          Verify in CI: `aapt dump permissions app-release.apk` must list
          INTERNET etc. Install the release APK on a phone and log in
          (acceptance for the earlier "login not working" report).

P0-C  Untested auto-deploy to production, with the wrong Dockerfile
  Where : deploy-api.yml (on push to rewrite/flutter-rust-postgres) vs
          fly-deploy.yml; root Dockerfile vs services/api/Dockerfile
  What  : Any push deploys. No tests, lint or image smoke test gate it. Two
          workflows are both named "Deploy API". deploy-api.yml deploys from the
          repo root, i.e. the ROOT Dockerfile, which runs as root and has no
          HEALTHCHECK; the hardened Dockerfile in services/api is only used by
          the manual fly-deploy.yml and by the CI docker job, so CI validates a
          different image than production runs.
  Fix   : One Dockerfile (services/api), one fly.toml, one deploy workflow that
          `needs:` the CI jobs, deploys only from main/tags, uses a GitHub
          Environment with required approval, and runs a post-deploy smoke test
          (/ready, register, login) that rolls back on failure. Pin
          superfly/flyctl-actions to a commit SHA (today it is @master and
          receives FLY_API_TOKEN).

P0-D  New handlers bypass rate limits, body/CORS layers and the status check
  Where : main.rs merge order; profile_handlers, comment_handlers,
          messaging_handlers (rich messages, typing, presence), call_handlers,
          http/verification.rs
  What  : Rate limiting, DefaultBodyLimit, CORS and TraceLayer are applied inside
          http::router() only. Everything merged afterwards gets none of them
          (only the global security headers + origin guard). Each module also has
          its own copy of authorize() that only verifies the JWT; only the core
          router calls users.is_active(). A suspended user keeps full access to
          profiles, comments, chat, and calls, and there is no brute-force or
          spam limit on Google login, comments, messages or call signalling.
  Fix   : One tower layer stack applied to the MERGED app, and one `AuthUser`
          extractor (JWT + status check + optional admin check) used by every
          handler. Delete the six duplicated authorize() functions. Add an
          authorisation test matrix: anonymous / suspended / other user / admin
          for every route.

P0-E  Profile listing queries decode NUMERIC as f64 (CONFIRM)
  Where : profile_handlers.rs ListingRow { price: f64 } for
          /api/profile/me/listings (the endpoint the app calls) and the public
          profile listings.
  What  : listings.price is NUMERIC(14,2); sqlx does not decode NUMERIC into f64.
          Expect a runtime decode error: "My listings" returns 503 and the public
          profile's listings are silently empty (unwrap_or_default()). This also
          breaks the "money is Decimal end to end" rule. No test covers it.
  Fix   : Use rust_decimal::Decimal serialised as a string (or cast in SQL) and
          add an integration test creating a listing then reading both endpoints.
          Move these queries into the listing repository.

P0-F  Cloudinary is unconfigured, so photo upload cannot work
  Where : main.rs falls back to UnconfiguredMediaSigner when env vars are absent;
          your AUDIT-RESPONSE and REWRITE-PROGRESS list Cloudinary as not done.
  What  : /api/media/signature returns a not-configured error, so listings cannot
          get photos; a listing site without photos is not launchable. The
          silent fallback also hides the misconfiguration.
  Fix   : Set CLOUDINARY_* on Fly, make production boot fail when they are
          missing, validate uploads server-side (see P1-5), add a smoke test.

4. P1 - FIX BEFORE REAL USERS
--------------------------------------------------------------------------------
P1-1  APP_ENV is never set in fly.toml, so every "production" guard is inert
      (PASSWORD_RESET_DEBUG block, mock verification block). Fail closed: treat
      FLY_APP_NAME (or an unset APP_ENV) as production. verification_provider
      uses panic!() when called without creds in production: return an error at
      startup instead of panicking inside a request path.
P1-2  Secrets are only length-checked. Reject known placeholders in
      .env.example / docker-compose.yml and require real entropy. Replace the
      scattered std::env::var calls with one typed Config (ALLOWED_ORIGINS and
      REDIS_URL are re-read per request today).
P1-3  Refresh rotation is no longer atomic. The new code SELECTs the token and
      then UPDATEs it with no row lock, so two concurrent refreshes can both
      succeed (double-spend), while a benign network retry of an already-rotated
      token revokes ALL of the user's sessions. Use SELECT ... FOR UPDATE (or an
      UPDATE ... RETURNING that decides the winner), add a short reuse grace
      window, and test concurrency.
P1-4  Username generator is broken. username_base() picks the suffix with
      `(1000..9999).find(|_| true)`, which is always 1000, so every collision
      retries the same candidate and gives up after 8 tries; users with the same
      first-4-letters + last initial end up with NO username, breaking public
      profiles and deep links. Use a random suffix, retry on unique-violation, and
      add a UNIQUE index on lower(username).
P1-5  Media/URL trust. photo_url (profile) and media_url (chat) accept any string:
      validate https + your Cloudinary host/folder, length, and content type;
      media_type, duration_seconds and reaction emoji are unvalidated (use
      allow-lists and bounds). Force the Cloudinary upload folder server-side.
P1-6  Google sign-in: reqwest::Client::new() has no timeout and each login makes a
      live call to Google (no rate limit, no caching). Use a shared client with a
      timeout, rate limit the route, and consider verifying ID tokens locally
      against Google's cached JWKS. Linking to an existing password account
      silently WIPES that account's password; with no email-sending path (below)
      those users cannot recover password login. Prefer: verify email ownership
      first, tell the user, keep a recovery path.
P1-7  Password reset still cannot work in production: no email sender exists, and
      PASSWORD_RESET_DEBUG logs the raw token. Add an EmailSender + SMTP/provider,
      remove the token logging, and add email verification at registration.
P1-8  Chat/call surface. Typing endpoints do not check the caller is a participant
      (anyone with a token can read/write typing state for any conversation id)
      and the typing map is process-global (breaks with >1 machine). TURN
      credentials are static env values handed to every signed-in user: use
      short-lived HMAC credentials. SDP offer/answer sizes and `kind` are not
      bounded/validated at the handler. Calls and messages need rate limits.
P1-9  Comments: list is ORDER BY created_at ASC LIMIT 200 with no pagination, so
      the newest comments disappear on busy listings; no listing-visibility check
      on read; the listing owner cannot moderate; no report path; no spam limit.
P1-10 Logging/observability: zero tracing::error! anywhere; every `Err(_)` in the
      new handlers drops the cause and returns a generic 503; failed login logs
      the raw email; output is plain text, not JSON; no request id; no metrics.
      One error type that logs its source once at the boundary fixes this.
P1-11 Tests are far below the surface area: 8 Rust tests and 8 Flutter tests for
      ~18,000 lines; none for comments, profile, Google, calls, reset, refresh
      reuse, rate limiting or the status check; DB tests `return` silently when
      DATABASE_URL is unset (so they pass without running); no router-level tests;
      zero golden tests, so visual parity with the old app is unproven.
P1-12 CI hygiene: workflows have `contents: write` and force-push failure logs to
      public ci-logs-* branches (a secret that reaches a log would be committed
      to the repo; upload masked artifacts instead); `continue-on-error` on
      toolchain steps; `--no-fatal-warnings`; duplicated build-apk workflows;
      scripts/ci.sh calls a workflow (build-apk-manual.yml) that no longer exists.
P1-13 Migrations use two schemes (0001..0012, then 202611260001/2). sqlx orders by
      number, so a future 0013 sorts before the timestamp ones. Pick one scheme
      now. Migration 0006 still contains a destructive DELETE.
P1-14 Missing migration tooling: the Firebase migration script and its Python
      helper are not in the snapshot, so docs/legacy-migration.md describes a
      process nobody can run. (If they exist locally, commit them; if not,
      rebuild per the earlier Section 8 requirements.)

5. P2 / POLISH
--------------------------------------------------------------------------------
  - HSTS "preload; includeSubDomains" is hard-coded by the app; apply HSTS at the
    edge, and only add preload after the final domain is fixed. CSP allows
    'unsafe-inline' scripts on public pages.
  - Release size: flutter_webrtc, record and audioplayers are heavy; ship an App
    Bundle / --split-per-abi and measure.
  - main.dart throws StateError in _boot for a missing API_BASE_URL in release;
    that surfaces as an endless splash. Render a clear fatal-config screen.
  - Move the raw-SQL handlers into repositories; adopt sqlx macros +
    `cargo sqlx prepare --check` so schema drift fails at compile time (it is how
    the f64/NUMERIC and participant_a bugs got in).
  - Typing/presence state belongs in Redis/DB once you run >1 machine.
  - Document and test the rollback plan (Fly releases + DB backups).
