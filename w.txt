3. LOGIN: STILL UNVERIFIED
--------------------------------------------------------------------------------
Client-side causes are mostly addressed, but these can still make it fail:
  - Server side: nothing proves DATABASE_URL/JWT_SECRET/REFRESH_TOKEN_SECRET are
    set on Fly. main.rs still has 10 "Unconfigured" references: a missing
    DATABASE_URL still boots a server that answers 503 to every login.
  - Local-clock check remains: api_client throws FormatException("Invalid
    session response") if server expiry is not after the phone's clock.
  - `signedIn` is still computed from local expiry, and restore() does not
    refresh. With a valid refresh token but an expired access token the app
    thinks you are signed out and shows the AuthSheet again; after a restart
    users are re-prompted roughly every access-token lifetime.
  - No single-flight refresh (concurrent 401s can sign the user out).
  - AuthSheet is a single form: no Google button (only the older auth_screen
    has it), no two-step email-then-password flow like the legacy modal, and
    "Forgot password" leads to a flow whose emails are never sent (below).
  - Root fly.toml is stale (auto_stop_machines="stop", min 0) next to the good
    services/api/fly.toml: two sources of truth.
Required to close: the diagnosis in v2 Part 2.2 (curl /ready, register, login;
fly secrets list; fly logs) with outputs pasted, and a release APK logging in on
a real phone.

4. NEW FINDINGS IN THIS SNAPSHOT
--------------------------------------------------------------------------------
  P0  Google sign-in account pre-hijacking. google_auth upserts by email and
      links to an existing PASSWORD account. Because email addresses are never
      verified at registration, an attacker can register victim@gmail.com with a
      known password first; when the victim later uses Google they land in the
      same account and the attacker still has the password. Fix: require email
      verification before accounts count as verified; on Google sign-in to an
      unverified password account, reset the password hash/revoke sessions, or
      refuse to link until the existing account is verified.
  P0  Google sessions have refresh_token = null and skip the users.status check
      (suspended users can sign in with Google). Issue a normal refresh token and
      reuse the same login path/guards.
  P1  Password reset still cannot work in production: there is no email sender
      (no lettre/SMTP/Resend dependency); the token is only logged when
      PASSWORD_RESET_DEBUG=1, and that log line prints the raw token and email.
      Add an EmailSender, send the link, delete the token logging.
  P1  Verification "mock" provider (verification_provider.rs) approves any ID
      of 11+ characters. Make it impossible to select unless APP_ENV is
      development/test, and make production startup fail if it is configured.
      docs/verification-provider.md correctly says not to store raw NIN/BVN;
      add a test enforcing that.
  P1  Admin is now checked through admin_roles in 4 places (users, comments,
      profile handlers). That is fine only if it is the SINGLE model: confirm
      users.is_admin is gone/unused, add the CLI grant/revoke, and add tests for
      every admin route (non-admin 403).
  P1  Rate-limiting, CORS default, media URL/signing validation, refresh reuse
      detection, error logging (still 0 tracing::error!), typed Config,
      placeholder secrets in .env.example and docker-compose.yml: all unchanged
      from pass 1 (P0-5, P0-10, P1-1..5 remain OPEN).
  P1  CI unchanged: triggers only on tag `ci`, `contents: write`, force-pushing
      log branches; DB tests still `return` silently when DATABASE_URL is unset
      (api_flow.rs, hardening.rs). There is still no PR/branch CI, no Docker
      build job, no android/ folder, no release-signing config, 0 golden tests.
  P2  The comment/profile handlers add many raw SQL queries outside the layered
      repositories and still use string SQL (no sqlx macros): another place for
      silent schema mismatches. Add router-level integration tests for each.
  P2  Onboarding is shown once before the shell; confirm it is skippable and
      never re-appears after a data clear that keeps the account.
