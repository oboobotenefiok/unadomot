0. HOW THIS WAS DONE (AND WHAT IT CAN'T TELL YOU)
--------------------------------------------------------------------------------
Static review of every backend file (services/api: ~3,450 lines of Rust, 5 SQL
migrations, Dockerfile, compose, CI workflow), every Flutter file (~1,800 lines),
the Firebase migration script, and the repo's own docs (REWRITE-PROGRESS.md,
PRODUCTION-READINESS.md, DEPLOYMENT.md).

NOT done: I did not compile, run, load-test or pen-test anything (the sandbox had
no Rust/Flutter toolchain and no network). Findings are from reading code and
cross-checking it against the SQL schema. Where I say "will fail" I traced it by
hand; confirm each P0 by running it. I did not review git history (use gitleaks
or trufflehog on the full history), the legacy Firebase rules that still sit in
the repo root, or any deployed infrastructure.


1. VERDICT
--------------------------------------------------------------------------------
NOT production ready. Treat v0.1.0 as an early alpha / architecture proof.

The foundations are good: clean hexagonal layering, parameterised SQL
everywhere, Argon2 passwords, HMAC-hashed rotating refresh tokens, Decimal
money, ownership enforced in SQL, graceful shutdown, readiness probe. That is
more discipline than most rewrites at this stage.

But the progress doc over-claims. Several items ticked "done" do not work:
  * Messaging is ticked done, but every messaging query references columns that
    do not exist in the schema (P0-1), and the app has no way to start a chat
    (P0-2).
  * "Verification" is ticked done, but approving a request never sets the
    verified flag (P0-8).
  * "Structured request logging / production readiness" is ticked, but no
    database error is ever logged (P0-10) and logs are plain text, not JSON.
  * "CI passes" is true, but CI never exercises messaging, verification,
    refresh, the Docker build, or a release APK - which is exactly where the
    defects are.
  * The Firebase migration, the Docker deployment and the release APK have
    each never been run successfully as written (P0-4, P0-7, P0-9).

Realistic status: about 40-50% of the main-branch feature set exists, and of
what exists, roughly half has launch-blocking defects. The good news is that the
fixes are mostly small and well-localised. Section 9 gives a work order.

Severity key
  P0 = blocks launch (broken feature, security hole, or cannot be deployed)
  P1 = fix before real users / before any traffic you care about
  P2 = hardening and operability; schedule it
  P3 = polish


2. WHAT IS GOOD (KEEP IT)
--------------------------------------------------------------------------------
  + Hexagonal split (domain / application / infrastructure / http) with traits,
    so repositories can be faked in tests.
  + All SQL is parameterised; I found no string-built queries (no injection).
  + Ownership is enforced inside the UPDATE/DELETE (WHERE landlord_id = $2).
  + Argon2id for passwords; refresh tokens stored only as HMAC-SHA256 hashes;
    rotation happens in one transaction; JWT validates iss/aud/exp, HS256 only.
  + rust_decimal + NUMERIC(14,2) with CHECK (price > 0); money travels as a
    string end to end. Correct choice.
  + Soft delete on listings; partial search index; sensible FK cascades.
  + Public listing page HTML-escapes everything and escapes "<" in JSON-LD.
  + Cloudinary uploads are server-signed (the API secret never reaches the app).
  + 2 MB body limit, nosniff / X-Frame-Options / Referrer-Policy on the main
    router, graceful SIGTERM shutdown, /health and /ready split.
  + Flutter: tokens in secure storage, offline cache, draft saving, timeouts,
    unit tests for the API client.


3. P0 - LAUNCH BLOCKERS
--------------------------------------------------------------------------------

P0-1  Messaging backend is broken against the real schema
  Where : services/api/src/infrastructure/postgres/messaging_repository.rs
          vs migrations/0001_initial_schema.sql
  What  : Every query selects/inserts conversations.participant_a and
          participant_b. The schema has no such columns; participants live in
          conversation_participants, and no migration adds them. Every
          conversation and message endpoint will fail with a SQL error, which
          the HTTP layer turns into an anonymous 503.
  Why it shipped: queries use sqlx::query_as with string SQL (not the query!
          macros), so nothing is checked at compile time; the only integration
          test covers register/login/listing and never touches messaging.
  Fix   : Decide on one model. Simplest: add participant_a/participant_b (UUID,
          NOT NULL, FK) plus CHECK (participant_a <> participant_b) and a
          UNIQUE index on (listing_id, LEAST(a,b), GREATEST(a,b)); drop the
          unused conversation_participants table. Then write integration tests
          for start / list / send / read / forbidden-access. Move to
          sqlx::query!/query_as! (+ `cargo sqlx prepare` in CI) so this class of
          bug becomes a compile error.

P0-2  A user cannot actually start a chat
  Where : http/mod.rs ListingResponse; listing_detail_screen.dart
  What  : ListingResponse does not expose landlord_id, and the Flutter "Chat
          with lister" button is onPressed: () {} (a no-op). The client has no
          way to know who to message. Separately, start_conversation trusts a
          client-supplied other_user_id: it never checks that the listing
          exists, that other_user_id actually owns it, or that the user exists.
          Anyone can create "conversations" attributed to any listing/user pair.
  Fix   : Server derives the counterpart from the listing
          (POST /api/listings/{id}/conversations, other = listing.landlord_id).
          Reject messaging your own listing. Return lister display name /
          verified flag on the listing response. Wire the button.

P0-3  Create-listing screen is unreachable
  Where : apps/flutter_app/lib (no references to CreateListingScreen)
  What  : ListingsScreen has no button/route to CreateListingScreen. The core
          landlord action cannot be performed in the app.
  Fix   : Add a "Post listing" FAB (and require sign-in/verification as you
          decide), plus "My listings" with edit / mark rented / delete - the
          API already supports PATCH/DELETE but the app has no UI for them.

P0-4  The Docker image cannot be built as written
  Where : services/api/Dockerfile, repo
  What  : (a) Dockerfile does COPY Cargo.toml Cargo.lock, but there is no
          Cargo.lock in the branch and .gitignore does not even mention
          target/, so the build fails at that line. (b) The builder is pinned to
          rust:1.82 while CI builds with "stable"; with no lockfile, transitive
          dependencies resolve to current versions that can require a newer
          rustc. (c) CI never builds the image, so nobody found out.
  Fix   : Commit Cargo.lock (this is a binary - lockfiles are mandatory). Pin
          the Rust image to the same toolchain CI uses (rust-toolchain.toml).
          Add a CI job: docker build + container smoke test (/ready against a
          Postgres service). Add .dockerignore (target/, .git, *.md).
          cargo-chef (or BuildKit cache mounts) for sane build times.

P0-5  Publicly known JWT secrets pass the startup check
  Where : main.rs (len >= 32 check), docker-compose.yml, .env.example
  What  : docker-compose.yml ships JWT_SECRET="change-me-to-a-random-string-of-
          at-least-32-bytes" (49 chars) and .env.example ships
          "replace-with-at-least-32-random-bytes" (37 chars). Both pass the
          length check, so anyone who runs the compose file (or copies the
          example) in production signs tokens with a secret published in the
          repo - i.e. anyone can forge a token for any user, including admins.
          Also: PRODUCTION-READINESS.md says REFRESH_TOKEN_SECRET is required
          and "separate from JWT", but the code silently falls back to
          JWT_SECRET and then to a hard-coded "development-refresh-secret".
  Fix   : Refuse to start if either secret matches a placeholder list or is
          not high-entropy (e.g. require base64/hex of >= 32 random bytes).
          Require REFRESH_TOKEN_SECRET explicitly and ensure it differs from
          JWT_SECRET; remove the hard-coded fallback. Remove secrets from the
          compose file (use env_file / secrets) and document `openssl rand
          -base64 48`. Read config once at startup into a typed Config struct
          (hash_refresh_token currently reads env vars on every call).

P0-6  Privilege escalation via ADMIN_EMAILS + unverified emails
  Where : http/verification.rs authorize_admin, application/auth.rs register
  What  : Admin rights are granted if the email *claim in the JWT* matches
          ADMIN_EMAILS. Registration does no email verification. If the real
          admin has not registered yet (or you add an address that doesn't have
          an account), anyone can register that address and become an admin
          who can approve/reject verifications and read every submitted
          document URL.
  Fix   : Do not authorise by an email string. Bootstrap admins by explicit
          one-time CLI/SQL (UPDATE users SET is_admin = true), authorise via
          users.is_admin only, and add email verification before any
          privileged action. Delete the admin_roles table (it duplicates
          users.is_admin and is unused).

P0-7  Owners can undo admin takedowns; removed listings stay public
  Where : http/mod.rs UpdateListingRequest.status, listing_repository.rs
  What  : The PATCH body accepts status: ListingStatus, whose variants include
          RemovedByAdmin. An owner can set that value on their own listing or,
          worse, flip an admin-removed listing back to "available". Separately,
          get() and the public /listing/{id} page only filter deleted_at, so
          rented and admin-removed listings are still served to the public
          (and indexed via og/JSON-LD tags that say InStock).
  Fix   : Owners may only toggle available <-> rented. Admin-only transition
          to removed_by_admin (with removed_by/removed_reason, which exist in
          the schema but no code writes them). Public GET/page should 404 or
          render "no longer available" for non-available listings. Add the
          admin endpoint (none exists to remove a listing or process reports).

P0-8  The verification feature does not verify anyone (and misleads users)
  Where : verification_repository.rs review(); public_pages.rs; Flutter
  What  : Approving a request only updates verification_requests. Nothing sets
          user_profiles.verified, so no user can ever become verified. Yet the
          public page hard-codes "Verified listing on UnaDomot" in every
          description - a false trust claim on every listing, which is a
          consumer-protection/reputation risk for a rental marketplace
          (rental scams are the central trust problem here). Also: the user
          "verifies" by pasting a Document URL into a text field - i.e. an ID
          document has to be hosted somewhere public by the user. No URL
          validation; review() doesn't check the request is still pending.
  Fix   : On approval set user_profiles.verified in the same transaction
          (and write the audit row in that transaction too - today audit
          logging happens after, so a failure leaves an unaudited approval).
          Upload IDs through a *private/authenticated* Cloudinary (or S3)
          upload, admins read via short-lived signed URLs. Show the verified
          badge only where true. Drop the unused verification_documents table
          (it stores id_number in plaintext).

P0-9  Account lifecycle is incomplete; migrated users are locked out
  Where : whole auth surface; PRODUCTION-READINESS.md "Migration"
  What  : There is no password reset, no email verification, no logout/revoke
          endpoint, no change-password, no account deletion, and no Google
          sign-in (the legacy app had Google; the migration doc tells migrated
          users to "use password reset or social login" - neither exists).
          Users migrated from Firebase get password_hash = NULL and therefore
          cannot ever log in. `users.status` ('active') is never checked, so
          there is no way to suspend an account, and a deleted/suspended user's
          JWT stays valid until it expires.
  Fix   : Build, in order: logout (revoke refresh token / all sessions),
          email verification, password reset (single-use, hashed, expiring
          token via an email provider), Google/OIDC sign-in with server-side
          ID-token verification, change password (revoking sessions), account
          deletion/export (NDPA - see P2). Check users.status on login and on
          refresh. Consider keeping access tokens <= 15 min.

P0-10  Production failures are invisible
  Where : every `.map_err(|e| XError::Repository(e.to_string()))`
  What  : There is not a single tracing::error!/warn! in the backend. Every
          database/sqlx error is converted to a string and then dropped by
          the HTTP layer, which returns a generic 503. In production you would
          see "503 service_unavailable" in the access log and have no idea why
          (this is also why P0-1 would be hard to diagnose live). Unique
          violations (e.g. two concurrent registrations of one email) also
          surface as 503 instead of 409.
  Fix   : Log the underlying error with request id / user id at the boundary
          (error! for 5xx), map sqlx unique/FK violations to 409/422, use JSON
          log formatting (tracing_subscriber .json()) as the docs claim, add a
          request-id layer. Add a panic hook / error reporting (Sentry).

P0-11  Release Android app will have no network access
  Where : CI workflow (flutter create at build time), no committed android/
  What  : apps/flutter_app/android/ is not in the repo; CI generates it with
          `flutter create` on every run. The generated *main* manifest does not
          declare android.permission.INTERNET (only the debug/profile manifests
          do). A release build produced by this pipeline cannot reach the API.
          The default API_BASE_URL is also http://10.0.2.2:3000 (emulator
          loopback, cleartext), and a release build with no --dart-define would
          silently ship pointing at it. Only a debug APK has ever been built;
          signing is documented but there is no build.gradle to edit.
  Fix   : Commit the platform folders (android/, ios/). Add INTERNET to the
          main manifest, set a real applicationId, configure release signing
          from CI secrets, make API_BASE_URL mandatory in release
          (assert(kReleaseMode ? url.startsWith('https://') : true)), build and
          install-test the release APK in CI, add R8/proguard review.

P0-12  Flutter sessions break after one hour and refresh tokens get lost
  Where : lib/state/app_state.dart, lib/api/api_client.dart
  What  : (a) restore() calls restoreSession(), which ignores an expired access
          token - and access tokens last 60 min. So after any restart more than
          an hour later the user is logged out even though a 30-day refresh
          token is sitting in secure storage; restore never tries to refresh.
          (b) After a successful silent refresh, the rotated tokens are updated
          in memory only and never written back to secure storage; the stored
          refresh token was just revoked server-side, so the next cold start
          fails. (c) createListing() and mediaSignature() pre-check `signedIn`
          (expiry) and throw 401 locally, so they never reach the code that
          would refresh. (d) Concurrent 401s each fire a refresh with the same
          refresh token; the second fails (token already rotated) and signs the
          user out. (e) signOut() is local only - the server token stays valid.
  Fix   : Single-flight refresh guarded by a Completer, persisted through a
          callback into AppState; restore() should refresh if the access token
          is expired; drop the local signedIn pre-checks; add a server logout.


4. P1 - FIX BEFORE REAL USERS
--------------------------------------------------------------------------------

Security / abuse
P1-1  Rate limiter is bypassable and can DoS you.
      http/mod.rs rate_limit keys on the first X-Forwarded-For value, which any
      client can spoof (unlimited bypass, and an unbounded in-memory HashMap
      that grows per unique spoofed value). With no proxy header every client
      shares the key "unknown" - one global 120 req/min bucket. Redis path
      opens a new connection per request, does INCR then EXPIRE non-atomically
      (a crash between them leaves a key with no TTL = permanent block), and
      silently falls back to memory on any error. It also wraps only the main
      router: public_pages and verification routers are merged afterwards and
      get no rate limit, no body limit, no security headers and no TraceLayer.
      Fix: trust XFF only from a configured proxy hop count (or use the
      connection's peer address via ConnectInfo), use a proper crate
      (tower_governor) or an atomic Lua/INCR+EXPIRE NX script with a pooled
      ConnectionManager, evict old buckets, and apply the layer stack to the
      *merged* router. Add much tighter limits for /auth/* (e.g. 5-10/min/IP
      plus per-email), message sending, and /media/signature.
P1-2  Credential-stuffing / enumeration. login() returns instantly for unknown
      emails but runs Argon2 for known ones (timing oracle); register returns
      409 for existing emails; no per-account lockout/backoff. Argon2 hashing
      runs on the async executor and will stall other requests under load -
      move to spawn_blocking (and consider tuned params).
P1-3  CORS fails open. Empty ALLOWED_ORIGINS => CorsLayer::permissive().
      Default must be deny; require explicit config in production.
P1-4  Media endpoints trust the client. add_media accepts any URL and any
      public_id: it should verify the URL is https://res.cloudinary.com/<your
      cloud>/... and the public_id matches, cap media per listing, validate
      position. /media/signature signs whatever `folder` the client sends -
      force the folder server-side (e.g. unadomot/listings/<user_id>), and add
      upload restrictions (allowed_formats, max size, resource_type=image) to
      the signed params. Both use the user's session without any per-user
      quota.
P1-5  Refresh-token hygiene: no reuse detection (replaying a rotated token
      should revoke the whole family), no cap on tokens per user, no cleanup
      job for expired/revoked rows, tokens built from two UUIDv4 strings
      instead of 32 bytes from OsRng.
P1-6  Weak input validation: email check is just contains('@')+contains('.');
      update_listing doesn't validate description/address/state/lga length or
      bedrooms/bathrooms/furnishing/property_type values; state/lga/property
      type are free text (no enum / Nigerian LGA list - the legacy app had
      one in data/); no max price. Add DB CHECK constraints for the enum-like
      text columns (status, user_type, property_type, furnishing).
P1-7  Listing PATCH semantics: Option<Option<T>> is deserialised so JSON null
      is indistinguishable from "absent" (serde needs deserialize_with), and
      the SQL uses COALESCE, so fields can never be cleared. A missing or
      someone-else's listing returns 403 instead of 404. Fix with explicit
      patch handling or a transaction that loads then updates.

Correctness / data
P1-8  list_messages orders ASC with LIMIT 100 OFFSET 0 and the handler never
      passes a page, so any conversation beyond 100 messages shows only the
      oldest 100 and the newest are unreachable. Use keyset pagination on
      (created_at, id) descending, then reverse for display.
P1-9  Messaging features that the schema promises but code doesn't do: unread
      state (read_at / last_read_at never updated), conversations.last_message
      and last_sender_id never set, no unread count, conversations list returns
      raw UUIDs with no counterpart name, listing title or snippet (the app
      prints "Listing <uuid>"). No push notifications and no realtime channel
      (SSE/WebSocket) - the legacy app had live chat. No block/report/abuse
      controls for a marketplace where scam messages are the main threat.
P1-10 Race conditions: find_or_create_conversation is select-then-insert with
      no unique constraint (duplicate conversations under concurrency);
      register is find-then-insert (second racer gets a 503, see P0-10);
      login() verifies the password and then calls find_by_email a second
      time (needless query and a TOCTOU window) - return the user from login.
P1-11 Missing indexes: messages(conversation_id, created_at), listing_media
      (listing_id), favorites(listing_id), conversations(participant_a/b) once
      fixed, listings(status, created_at DESC) partial index for the default
      browse sort (current index leads with state/lga so "newest first"
      sorts in memory). Add pg_stat_statements and review EXPLAIN on browse.
P1-12 Unused/dead schema: reports, checkout_notices, admin_roles,
      verification_documents, listings.expires_at/view_count, removed_* columns
      have no code behind them. Either build the features or remove the tables
      so the schema reflects reality (and does not store a plaintext id_number).
P1-13 Migrations run at process startup on every replica. Fine for one box,
      risky for rolling deploys (long locks, concurrent starters, failed
      migration = crash loop). Run migrations as a separate release step, make
      each backward compatible (expand/contract), and test them against a copy
      of production data. uuid_generate_v4()/uuid-ossp needs extension rights;
      gen_random_uuid() is built in (PG13+).
P1-14 Startup behaviour: if DATABASE_URL is missing the server happily boots
      in "unconfigured" mode and answers 503 forever; same for missing
      Cloudinary config. Fail fast. Pool has max 10 connections with no
      acquire/idle/statement timeouts; add acquire_timeout, statement_timeout,
      and a request TimeoutLayer so slow queries can't pin the pool.
P1-15 Public page/SEO issues: sitemap is returned as text/html (must be
      application/xml), lists only the first 50 listings with no pagination or
      lastmod, JSON-LD datePosted is "now" on every render (use created_at),
      og-default.jpg is referenced but not provided, price is rendered as
      "800000.00" with a hard-coded "/year" and ₦, the deep link
      unadomot://listing/<id> needs an https App Link/Universal Link for real
      sharing, and no robots.txt. Add Cache-Control/ETag and a CSP.

Deployment / CI
P1-16 CI gaps: `cargo fmt` (not --check) so formatting never fails the build;
      the DB integration test silently passes when DATABASE_URL is unset (it
      `return`s) - make it fail; only 4 backend tests and 7 Flutter tests exist
      for ~5,200 lines; no tests at all for refresh rotation, messaging,
      verification, authorisation failures, rate limiting, public pages. No
      cargo audit / cargo deny, no Dependabot, no Flutter `pub outdated` gate,
      no migration test, no container build, no coverage, no secret scanning.
      flutter analyze runs with --no-fatal-infos.
P1-17 docker-compose is dev-only but documented as the deploy path: hard-coded
      DB credentials, Postgres port 5432 published to the host, no restart
      policy, no REDIS_URL / REFRESH_TOKEN_SECRET / CLOUDINARY_* /
      ALLOWED_ORIGINS / ADMIN_EMAILS, no volume backup story, API runs as root
      with no HEALTHCHECK. Provide a separate production compose/k8s manifest
      with TLS termination, secrets, resource limits and non-root user.


5. P2 - HARDENING AND OPERABILITY
--------------------------------------------------------------------------------
P2-1  Observability: JSON logs, request IDs propagated to responses, RED metrics
      (Prometheus /metrics - already on your TODO), DB pool gauges, tracing
      spans per use case, Sentry (backend + Flutter), uptime checks on /ready,
      alert rules (5xx rate, p95 latency, pool saturation, auth failures).
P2-2  Backups and DR: automated Postgres backups with *tested* restores and PITR,
      documented RPO/RTO, Cloudinary asset retention, secrets rotation
      runbook. The doc says "restore from the pre-migration backup" but there
      is no backup procedure to restore from.
P2-3  Privacy/compliance (Nigeria Data Protection Act 2023 and app-store
      policies): you collect phone numbers, IDs for verification, location and
      private messages. Need a privacy policy and terms (the legacy app had
      Privacy/Terms pages; the rewrite has none), consent, data export and
      deletion, retention periods for messages/ID documents/refresh tokens/
      audit logs, encryption at rest for ID documents, and an access policy for
      admins. Play Store requires a data-safety form and (for user-generated
      content) in-app report/block.
P2-4  Admin surface: audit log exists but only for verification review; no
      admin UI/API for reports, listing takedown, user suspension, or granting
      admin. Audit rows should be written in the same transaction as the action.
P2-5  Dependencies/supply chain: commit lockfiles for both apps (pubspec.lock
      too), pin the Flutter version in CI instead of `stable`, enable
      cargo-deny, review that 12 Flutter packages are behind and
      flutter_secure_storage is two majors behind.
P2-6  Config hygiene: one typed Config loaded and validated at startup;
      remove scattered std::env::var calls in request paths (PUBLIC_WEB_URL is
      read per request; defaults to https://unadomot.com, a domain you may not
      own); distinguish dev/staging/prod.
P2-7  Repo hygiene: android-error.txt (a committed CI log), the legacy Firebase
      web app still occupies the repo root next to the rewrite (components/,
      pages/, firestore.rules ...), no root-level .gitignore entries for
      target/, .dart_tool/, build/, Cargo.lock isn't tracked, scripts/
      sync-ci-errors.sh force-deletes and re-pushes the v0.1.0 tag and release
      on every run (you can never trust a tag) - use immutable semver tags
      and a proper release workflow. Move to a clear monorepo layout.
P2-8  Performance: offset pagination degrades on deep pages (keyset by
      created_at,id); browse issues a second query for media (fine) but there
      is no caching/ETag; no full-text or fuzzy search (legacy had search and
      map); `listings` filters are exact-match and case-sensitive (Rivers vs
      rivers); add pg_trgm or tsvector search and bounding-box/PostGIS for map.
      Run a k6 load test against a production-sized dataset before launch.
P2-9  Mobile architecture: a single hand-rolled ChangeNotifier and static
      Map<String,dynamic> payloads; introduce typed models for every response
      and a state-management/DI approach (Riverpod/Bloc) before the app grows.
      Add an https-only network security config and certificate-pinning
      decision.


6. P3 - FLUTTER UX / POLISH
--------------------------------------------------------------------------------
  - Error messages: ApiClient throws "Request failed (400)" and discards the
    server's validation message, so users never learn what to fix. Parse
    {error:{code,message}} and surface it. TimeoutException/FormatException are
    not caught; the Cloudinary upload and refresh calls have no timeout.
  - Browse: loads page 1 only (no infinite scroll even though the API
    paginates), no search/filter UI, no empty/error retry states beyond a
    pull-to-refresh, Image.network without caching/placeholder/error widget.
  - Chat: every bubble is left-aligned because the client never learns the
    current user's id; no timestamps/grouping/optimistic send/retry.
  - Create listing: price field accepts "1e5" or "1,000" style input that the
    server will reject; state is a free-text default "Rivers" instead of a
    picker; only one photo; no upload progress; failure after the listing is
    created but before the photo attaches leaves an orphan photo-less listing
    (do create+media atomically or allow retry).
  - Offline cache: unbounded growth, no TTL, not cleared on sign-out (a
    previous user's drafts/favorites remain on a shared device).
  - Favorites exist only in local SQLite; the server `favorites` table has no
    endpoints, so favorites don't sync and disappear on reinstall.
  - Accessibility/i18n: none yet (legacy had a high-contrast mode and
    light/dark themes). Add semantics labels, text scaling, dark theme,
    localisation scaffolding.


7. FEATURE PARITY GAP VS main (what users lose on migration)
--------------------------------------------------------------------------------
Implemented in rewrite (some broken - see above): email/password auth, browse,
listing detail, create listing + one photo, offline listing cache, drafts,
messaging screens, verification request screen.

Missing in rewrite (exists on main): Google sign-in, email verification,
password reset, user profiles (view/edit/public profile, username routes),
favorites sync and Favorites page, search + filters UI, interactive map with
clustering and geocoding, listing-by-code, share, notifications, real-time
chat, reports/moderation, checkout notices, admin page, privacy/terms pages,
accessibility modes, PWA/web access (the rewrite is Android-only; there is no
iOS or web client, and the old Netlify site would need to remain or be
replaced). Decide explicitly which of these are launch scope and which are
deliberately dropped, and tell users.


8. FIREBASE MIGRATION SCRIPT (scripts/migrate-firebase.mjs) - WILL NOT RUN
--------------------------------------------------------------------------------
  * `INSERT ... ON CONFLICT (email)` fails: the only unique index is on
    lower(email) (an expression index), so Postgres reports "no unique or
    exclusion constraint matching the ON CONFLICT specification". Use
    ON CONFLICT ((lower(email))) DO NOTHING, and compare with lower() on every
    lookup.
  * Inserts listings with status 'active', but the app/ListingStatus use
    'available'. Even if rows loaded, browse (status = 'available') would
    hide every migrated listing. (Add a CHECK on status so this fails loudly.)
  * price falls back to 0, which violates CHECK (price > 0); string prices
    from Firestore aren't normalised. Listing created_at/updated_at aren't
    carried over, so history is lost (and ordering by newest is wrong).
  * Field names (ownerEmail, landlordEmail, propertyType, isAgentListing,
    media[].publicId) are guesses; verify against real Firestore documents.
    Listings whose owner has no matching user are silently skipped.
  * No package.json exists, so `firebase-admin` and `pg` are undeclared.
  * Users migrate with password_hash NULL and there is no reset/social flow
    (P0-9). Favorites query matches `data.email` which may not exist on
    favorites documents. Messages, verification state, ratings and
    notifications are not migrated at all.
  * No transaction, no batching, sequential awaits per row. The "safe to
    rerun" claim is only partly true: media is inserted only when the listing
    row is newly created, so a failure between the listing insert and its media
    inserts leaves that listing permanently without photos on every rerun.
  Fix: write it in a transaction per entity with batches, add a staged
  rehearsal against a copy of production, a reconciliation report (counts,
  checksums, orphan check), and a dry run that actually validates every row
  against the new constraints.
